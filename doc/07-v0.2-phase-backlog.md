## Standing design constraints

Carried from the S23 security review, honored by every slice since, and **not
retired by this phase closing**. Any new frame must obey them:

1. **Authorize in the domain**, via `_require_host`, exactly like
   `set_item`/`reveal`/`reset`. The frontend's `isHost` is a rendering affordance,
   never the boundary.
2. **Frames carry a target id and no actor id.** The actor is the socket's
   handshake identity — so a client cannot attribute an action to someone else
   within its own socket.
3. **Validate the target** in the domain: it must be a current member, and the
   host cannot target themselves.
4. **Log actor / target / room / outcome** for actions that remove people or move
   authority, so a session is explicable after the fact.

The monochrome rule and the token set in [06-design-language.md](06-design-language.md)
govern any new UI. Grey is not colour.

## Known limitation — `attach` impersonation

Accepted, not fixed; the motivation for V3 below. `attach` authenticates on
`participant_id` alone (membership only) and `room_view` broadcasts every
participant id plus `host_id`, so any member can open a second socket as another
participant — the host included — and drive host-only actions. Since V5 deleted
the unauthenticated HTTP routes (D-50) this is the **only** remaining route to
host-only actions without host authority, confirmed by a working
proof-of-concept during V5's review.

Every attacker here is already an invited teammate: the unguessable code is a
room's only barrier (D-29) and the tool is no-auth throughout (D-9).
**Decided (D-51):** the tool will be deployed as an internal team tool, so V3 is
**nice-to-have, not a blocker**. Revisit if the tool ever goes somewhere less
trusted than a team room.

## Backlog

### V3 — Per-participant session token · `TODO` · nice-to-have, not a blocker (D-51)

Close the `attach` gap above — since V5 it is the entire authorization perimeter,
and this is the last route to host-only actions without host authority. Shape, per
the S23 review: `Participant` gains a `token` (`secrets.token_urlsafe()`);
create/join return it to that caller only; `room_view` never carries it; `attach`
requires it and compares with `hmac.compare_digest`, keeping the failure response
identical to the unknown-id case so it is not a membership oracle. Client-side,
`session.ts` already persists `{code, participantId}` and stores one more string.
Not user-visible, so the no-account stance of D-9 is untouched.
**Refs:** D-9, D-29, D-38, D-39, D-50, D-51.
*Carried from the v0.1 phase, where it was specified but never built.*

## Unowned loose ends

Not workitems — recorded so they are not rediscovered as surprises. All four come
from the slices v0.1 dropped rather than carried (**D-54**). Any of them can be
promoted into the backlog above if this phase decides to own it.

- **No `Origin` check on `/ws/rooms/{code}`** before `accept()`. Defence-in-depth
  against a hostile page only — a non-browser client forges `Origin` freely — and
  no substitute for V3. CORS is not the lever: browsers do not apply it to
  WebSocket handshakes, and every privileged action is WS-only. **Refs:** NFR-3,
  D-28, D-50.
- **`:focus-visible` is partial.** Present on buttons, inputs, and the header
  controls; not consistent everywhere. Match the existing treatment rather than
  inventing one (doc/06).
- **The two terminal room views take no focus** when they replace the room, so a
  screen-reader user is not told the page changed. A live region does not fix it —
  one created with its content already present does not reliably announce — so
  this wants focus management. Both views are in `pages/Room.tsx`.
- **Legacy alias tokens in `main.scss`** — `--border`, `--text`, `--text-h`,
  `--code-bg`, `--accent`, `--accent-bg`, `--accent-border`, `--sans`, `--heading`,
  `--mono`. Five are entirely unused, the rest have one or two uses. Do not use
  them in new code; retire them whenever the stylesheet is next opened (doc/06).

Slice ids also survive in code comments (S21 in `ParticipantsMenu.tsx`, S22 beside
`messages.REMOVED_MESSAGE` and the deck copy, S10 beside the log-level knob in
`main.py`). Read a slice id in code as "a known loose end, unowned" — D-54 says why
they were left in place.

## Out of scope (this phase)

Inherited unchanged from [02-current-scope.md](02-current-scope.md) until this
phase says otherwise: no accounts or authentication, no persistence or history, no
backlog/ticket management or integrations, no distribution charts, no timers, no
i18n, no mobile-native. Spectators as a distinct role remain out. Banning a
removed participant is out (D-15) — removal is not a ban.

On decks, V4 retired "no multiple or custom decks" only as far as its own scope
went. Still out: **T-shirt sizing and special cards** (`?`, coffee) — decks are
numbers-only — along with **named or saved decks**, **more than one deck per
room**, and **changing the deck after creation**.
