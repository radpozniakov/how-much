## Goal

a participant — and close out the deployment, polish, accessibility, and copy work
still outstanding. The target is a v0.1 you can hand to a team and deploy.

## Standing design constraints for V1/V2

Carried from the S23 security review and not optional:

1. **Authorize in the domain**, via `_require_host`, exactly like
   `set_item`/`reveal`/`reset`. The frontend's `isHost` is a rendering affordance,
   never the boundary.
2. **New frames carry a target id and no actor id.** The actor is the socket's
   handshake identity, as with every existing round frame — so a client cannot
   attribute an action to someone else within its own socket.
3. **Validate the target** in the domain: it must be a current member, and the
   host cannot target themselves.
4. **Log actor / target / room / outcome** for both actions. These are the first
   frames that remove people or move authority; a session should be explicable
   after the fact.

## Known limitation — `attach` impersonation

Accepted, not fixed, going into this phase. `attach` authenticates on
`participant_id` alone (membership only) and `room_view` broadcasts every
participant id plus `host_id`, so any member can open a second socket as another
participant — including the host — and drive host-only actions. Everything the tool
exposed before this phase is undone by a reset; **the room-control pair is not.** V1
writes `host_id` durably, and the displaced host has no route back while the impostor
stays connected. V2 goes further and is the sharper of the two: an impostor can put
real participants out of the room, and no reset brings them back — they have to be
told the code again and rejoin, losing their vote. Both have now **shipped**, so this
is present tense and V3's promotion criterion below is live rather than hypothetical.

Two things blunt V2's edge relative to V1, without removing it. Removal is *not* a
ban (D-15), so the ejected participant can walk straight back in with the code they
already hold — where a displaced host cannot restore their own role. And every
removal is now **logged** with actor, target, room, and outcome (constraint 4), so an
impersonated session is at least reconstructible after the fact, which is exactly
what that constraint was written for.

The judgement is unchanged: a room's only barrier is its unguessable code (D-29), so
every attacker here is already an invited teammate, and the tool has taken a no-auth
stance throughout (D-9). Shipping V1/V2 without closing this is a deliberate call.
The fix is tracked as **V3** and is small; promote it to a blocker if the tool ever
goes somewhere less trusted than a team room.

## Backlog

### V1 — Host handover · `DONE`

**Goal:** the host hands the host role to another participant and stops being
host. It is a *move* of permissions, not a grant: exactly one host at a time, no
co-hosts, no residue. The new host can hand it on again, and so on indefinitely.

Fits the domain as it stands — `Room` already holds a single `host_id`, so the
handover is one assignment. Unlike the disconnect-driven auto-transfer (D-13) there
is **no** transient `host_id: null`, so the host UI does not flicker through an
unowned state.

**Decided — the outgoing host becomes a full participant, and votes.** Once they
hand over they are an ordinary participant in every respect, **including if they had
opted out of voting while host**. The opt-out was a facilitator privilege attached to
the role, not to the person; it does not follow them out of it.

This needs **no new code**, because both sides already key on *who is host right
now* rather than on a stored per-participant flag:

- Domain — `cast_vote`'s guard is `participant_id == self.host_id and not
  self.host_voting` (`models.py`). The instant `host_id` moves, the outgoing host no
  longer matches it and may vote.
- UI — the eligible-voter set is
  `participants.filter(p => host_voting || p.id !== host_id)` (`Room.tsx:93-96`), so
  they reappear in the deck and in the vote-progress denominator on the next
  snapshot.

The mirror case **is** the real work: **reset `host_voting` to `true` on handover**,
so the incoming host does not silently inherit an opt-out they never chose (which
would leave them with no deck and excluded from the denominator). There is a direct
precedent in the domain — `remove_participant` already does exactly this when a host
*leaves* and the role auto-transfers (`models.py:125-126`, D-13). A deliberate
handover matches that path. Both hosts end up voters; either can opt out afterwards.

Visible consequence, mid-round: the denominator grows as the outgoing host rejoins
the voter pool — a round at `5/6` becomes `5/7`. This does **not** block anything:
`reveal` is unconditional in the domain, with no all-voted gate (D-12), so the host
can still reveal a partial round and the stats cover the votes actually cast.

**Settled while building:**

- **Timing — legal at any point, including after reveal.** Confirmed, and it needed
  an argument rather than a shrug: `RoundRevealed` guards the *inputs* to
  `results()` (`revealed` and `votes`), and a handover writes neither, so a revealed
  round survives it byte for byte. Decisive point against locking it — a host who
  reveals and then needs to leave would have to `reset`, destroying the results the
  room is reading, in order to hand over. See D-45 and `RoundRevealed`'s docstring.
- **Feedback — snapshot-only.** No new frames, no toast, no live-region
  announcement. The D-36 broadcast already makes host controls appear for the new
  host and vanish for the old one, which is the feedback. S20 owns interaction
  polish and S22 owns the copy; building either here would fragment them.

**Surface:** a per-row action in the S23 participants roster (which was built as
the anchor for exactly this — its rows are inert text and the panel is
`role="group"` until real menuitems exist). Any new UI follows
[06-design-language.md](06-design-language.md) — monochrome, state by border and
content rather than color.

**Refs:** FR-20 (to write), FR-7, FR-14 · D-13, D-14 · roster anchor S23.

### V2 — Remove a participant · `DONE`

**Goal:** the host removes a participant from the room.

With no accounts, removal is **not a ban**: the removed person still has the room
code and can rejoin as a fresh participant (D-15). Scoped as "remove," and that is
**enough for v0.1** — a real ban needs per-room state that does not exist today, so
it stays out of scope in [02-current-scope.md](02-current-scope.md). Pinned by test
rather than left implicit, so a later reader finds a decision instead of a gap.

`remove_participant_by_host` guards (`_require_host`, self-target, membership) and
delegates to the same `remove_participant` primitive the disconnect path uses — the
same effect under different authority. That delegate's D-13 auto-transfer branch is
unreachable here, and provably: it fires only for the id the self-target guard
rejects. So a removal never moves the role and never empties the room, which is why
it needs no `empty_since` stamp and stays out of `store.leave`.

**Settled while building** — the four open questions, in order:

- **What the removed participant sees — a dedicated `removed` slug and its own
  terminal notice.** Silence would have worked in the narrow sense: their socket
  closes, the client waits a second, re-`attach`es, is refused, and lands on the
  rejoin prompt. But the honest reason would be overwritten by a misleading
  "Participant is not in this room" after a detour through "reconnecting", so a
  removal would read as a stale session. The slug is protocol, not copy — S22 still
  owns the wording, which lives server-side beside the slug it travels with. This
  made `removed` the **first mid-session error that is terminal**, a category the
  client's phase-based terminality could not express; see D-47.
- **Socket teardown — `apply_and_evict`, which *uses* the single-owner logic rather
  than dodging it.** It detaches the target's socket from the manager map itself, so
  the removed socket's own `finally` gets `False` from `unregister` and correctly
  skips a leave for someone already gone — no duplicate broadcast, nothing to
  suppress. The detach deliberately precedes the broadcast, so the removed client
  never receives a snapshot of a room it is not in.
- **Rejoining immediately — accepted, no cooldown.** Consistent with D-15 and with
  the code being a room's only barrier (D-29). The terminal notice means they are not
  *handed* a rejoin form, but the link still works.
- **Interaction with V1 — confirmed, and tested both ways.** The host cannot remove
  themselves (constraint 3); a host who wants out hands over first, then leaves. And
  authority follows the role: after a handover the new host can remove, including
  removing whoever used to be their host.

One question the item did not carry but had to answer: **it is not locked after
reveal**, though unlike a handover it genuinely rewrites a revealed round — dropping
the target's vote changes the average and consensus. That is the leave path's
documented, tested behavior reached by a deliberate trigger, and locking it would
force a `reset`, destroying the results the room is reading, as the price of removing
someone. See D-47 and `RoundRevealed`'s docstring.

**Surface:** a second per-row action in the S23 roster, beside V1's "Make host" and
with the same two-step confirm. The row became **two fixed button positions — Make
host, then Remove — and the confirm controls keep fixed sides: Cancel first, Confirm
second, whichever action is pending.** So a pending confirm hides both actions rather
than disabling one, and the accept/reject pair is always in the same place. Neither
button ever moves; the trade is that only the removal is a press-twice-in-place, and it
required real focus management to keep the handover completable from the keyboard —
see D-47, which records both. Monochrome per
[06-design-language.md](06-design-language.md) — a person-minus glyph rather than a
trash can, since removal deletes nothing.

**Refs:** FR-21, FR-5, FR-6, FR-17 · D-15, D-18, D-47 · roster anchor S23.

### V3 — Per-participant session token (optional hardening) · `TODO`

Close the `attach` gap above. **Not** a blocker on V1/V2 — sequencing decided at
the top of this phase.

Shape, per the S23 review: `Participant` gains a `token`
(`secrets.token_urlsafe()`); create/join return it to that caller only;
`room_view` never carries it; `attach` requires it and compares with
`hmac.compare_digest`, keeping the failure response identical to the unknown-id
case so it is not a membership oracle. Client-side, `session.ts` already persists
`{code, participantId}` and stores one more string.

Not user-visible, so it does not touch the no-account stance of D-9 — no signup,
no login, nothing to remember.

**Refs:** D-9, D-29, D-38, D-39.

## Out of scope (this phase)

Unchanged from [02-current-scope.md](02-current-scope.md) apart from the two
features above: no accounts or authentication, no persistence or history, no
backlog/ticket management or integrations, no multiple or custom decks, no
distribution charts, no timers, no i18n, no mobile-native. Banning a removed
participant is explicitly **not** in V2. Spectators as a distinct role remain out.
