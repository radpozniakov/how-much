## Goal

Give the host real control over the room — hand the role to someone else, remove
a participant, choose the room's card values — and close out the deployment,
polish, accessibility, and copy work still outstanding. The target is a v0.1 you
can hand to a team and deploy.

## Standing design constraints

Carried from the S23 security review. V1/V2 honored them; any new frame must too:

1. **Authorize in the domain**, via `_require_host`, exactly like
   `set_item`/`reveal`/`reset`. The frontend's `isHost` is a rendering affordance,
   never the boundary.
2. **Frames carry a target id and no actor id.** The actor is the socket's
   handshake identity — so a client cannot attribute an action to someone else
   within its own socket.
3. **Validate the target** in the domain: it must be a current member, and the
   host cannot target themselves.
4. **Log actor / target / room / outcome** for actions that remove people or move
   authority, so a session is explicable after the fact.

## Known limitation — `attach` impersonation

Accepted, not fixed. `attach` authenticates on `participant_id` alone (membership
only) and `room_view` broadcasts every participant id plus `host_id`, so any
member can open a second socket as another participant — the host included — and
drive host-only actions. V1 and V2 raised the stakes: a displaced host has no
route back while the impostor stays connected, and a removed participant is out
until re-invited (blunted by removal not being a ban, D-15, and by every removal
being logged, constraint 4). Since V5 deleted the unauthenticated HTTP routes
(D-50), this is the **only** remaining route to host-only actions without host
authority — confirmed by a working proof-of-concept during V5's review. The fix
is **V3**.

Every attacker here is already an invited teammate: the unguessable code is a
room's only barrier (D-29) and the tool is no-auth throughout (D-9).
**Decided (D-51):** the tool will be deployed as an internal team tool, so V3 is
**nice-to-have, not a blocker** on v0.1. Revisit if the tool ever goes somewhere
less trusted than a team room.

## Backlog

### V1 — Host handover · `DONE`

The host hands the role to another participant — a *move*, not a grant: exactly
one host at any moment, the outgoing host becomes an ordinary voter, the incoming
host gets `host_voting` reset so they never inherit an opt-out. Legal at any
point in a round, including after reveal. Surfaced as a per-row roster action
with an inline two-step confirm. Rationale and consequences: **D-45**; the
panel's ARIA shape: **D-46**.
**Refs:** FR-20, FR-7, FR-14 · D-13, D-45, D-46.

### V2 — Remove a participant · `DONE`

The host removes another participant: the leave path under host authority, so
the target's vote goes with them and their connection ends with a terminal
`removed` notice. Not a ban — they can rejoin at once with the code they hold.
Second per-row roster action, same two-step confirm on fixed button positions.
Rationale, socket-teardown ordering, and the confirm-row trade-offs: **D-47**.
**Refs:** FR-21, FR-5, FR-17 · D-15, D-18, D-47.

### V3 — Per-participant session token · `TODO` · nice-to-have, not a blocker (D-51)

Close the `attach` gap above — since V5 it is the entire authorization
perimeter, and this is the last route to host-only actions without host
authority. Shape, per the S23 review: `Participant` gains a `token`
(`secrets.token_urlsafe()`); create/join return it to that caller only;
`room_view` never carries it; `attach` requires it and compares with
`hmac.compare_digest`, keeping the failure response identical to the unknown-id
case so it is not a membership oracle. Client-side, `session.ts` already
persists `{code, participantId}` and stores one more string. Not user-visible,
so the no-account stance of D-9 is untouched.
**Refs:** D-9, D-29, D-38, D-39, D-50.

### V4 — Host-chosen card values · `DONE`

The host may name the room's card values when creating it, in one optional
comma-separated field; left blank, the room gets the Fibonacci default. The deck
became room state riding the snapshot, validated only at the create boundary,
and fixed for the room's life. Bounds were tightened after shipping — `1`–`999`,
2–12 cards, the default lost its `0` (D-49); for current figures read FR-22.
Rules and rationale: **D-48**, **D-49**.
**Refs:** FR-22, FR-9, FR-16 · D-7, D-8, D-48, D-49.

### V5 — Retire the unused HTTP routes · `DONE`

Deleted the S3/S4 HTTP round routes, the unauthenticated participant `DELETE`,
and the T1 `/ws` echo — D-35 *executed*, and no new FR since NFR-1 already
described the end state. Sequenced ahead of V3 because the `DELETE` route was
exploitable with a `curl` one-liner, and review showed the five round routes
were forgeable too (identity from the request body). Backend 279 → 246 tests;
frontend and e2e untouched. Findings, test fallout, and the mutation-testing
lesson: **D-50**.
**Refs:** NFR-1, NFR-6 · D-5, D-35, D-36, D-50.

### S10 — Deployment polish · `TODO`
Finalize Docker/compose for a deployable setup, config, and run docs. The CORS
item changed shape after V5: browsers do not apply CORS to WebSocket handshakes,
and every privileged action is now WS-only, so tightening `allow_origins` (D-28)
protects little that matters. The task that replaces it is an **`Origin` check

page only, since a non-browser client forges `Origin` freely, and no substitute
for V3. **Refs:** NFR-3, D-28, D-50. Independent of everything else here.

### S21 — Accessibility & responsiveness pass · `TODO`
Keyboard navigation, visible focus states, contrast, semantic markup, and
small-screen usability across all screens — the roster panel included.

wants focus management, which is this slice's lane rather than V2's.

## Out of scope (this phase)

Unchanged from [02-current-scope.md](02-current-scope.md) apart from the features
above: no accounts or authentication, no persistence or history, no
backlog/ticket management or integrations, no distribution charts, no timers, no
i18n, no mobile-native. Banning a removed participant is explicitly **not** in
V2. Spectators as a distinct role remain out.

V4 retires "no multiple or custom decks" only as far as its own scope goes. Still
out: **T-shirt sizing and special cards** (`?`, coffee) — decks are numbers-only —
along with **named or saved decks**, **more than one deck per room**, and
**changing the deck after creation**.
