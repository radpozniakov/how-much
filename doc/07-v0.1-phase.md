> ([archive/phase1-mvp-backlog.md](archive/phase1-mvp-backlog.md)); the UX/UI
> phase made it look and feel right

> This phase adds the **room-control features** the redesign left as anchors, and
> finishes the four slices those phases carried forward.

## Goal

Give the host real control over the room — hand the role to someone else, remove
a participant, choose the room's card values — and close out the deployment,
polish, accessibility, and copy work still outstanding. The target is a v0.1 you
can hand to a team and deploy.

The card-values item (V4) is the one that widens the phase past "room control" as
originally framed: it configures the *round*, not the people in it. It is here
because it is small, it is the first creation-time option a room has ever had, and
v0.1 is the release where a fixed Fibonacci deck starts to look like a limitation
rather than a decision.

## Standing design constraints for V1/V2

Carried from the S23 security review and not optional:

1. **Authorize in the domain**, via `_require_host`, exactly like
   `set_item`/`reveal`/`reset`. The frontend's `isHost` is a rendering affordance,
   never the boundary.
2. **New frames carry a target id and no actor id.** The actor is the socket's
   handshake identity, as with every existing round frame — so a client cannot
   attribute an action to someone else within its own socket.
3. **Validate the target** in the domain: it must be a current member, and the
   host cannot target themselves.
4. **Log actor / target / room / outcome** for both actions. These are the first
   frames that remove people or move authority; a session should be explicable
   after the fact.

## Known limitation — `attach` impersonation

Accepted, not fixed, going into this phase. `attach` authenticates on
`participant_id` alone (membership only) and `room_view` broadcasts every
participant id plus `host_id`, so any member can open a second socket as another
participant — including the host — and drive host-only actions. Everything the tool
exposed before this phase is undone by a reset; **the room-control pair is not.** V1
writes `host_id` durably, and the displaced host has no route back while the impostor
stays connected. V2 goes further and is the sharper of the two: an impostor can put
real participants out of the room, and no reset brings them back — they have to be
told the code again and rejoin, losing their vote. Both have now **shipped**, so this
is present tense and V3's promotion criterion below is live rather than hypothetical.

Two things blunt V2's edge relative to V1, without removing it. Removal is *not* a
ban (D-15), so the ejected participant can walk straight back in with the code they
already hold — where a displaced host cannot restore their own role. And every
removal is now **logged** with actor, target, room, and outcome (constraint 4), so an
impersonated session is at least reconstructible after the fact, which is exactly
what that constraint was written for.

The judgement is unchanged: a room's only barrier is its unguessable code (D-29), so
every attacker here is already an invited teammate, and the tool has taken a no-auth
stance throughout (D-9). Shipping V1/V2 without closing this is a deliberate call.
The fix is tracked as **V3** and is small; promote it to a blocker if the tool ever
goes somewhere less trusted than a team room.

**`attach` is not the cheapest route to this, though — and that was missed above.**
`DELETE /{code}/participants/{participant_id}` reached V2's effect with no socket, no
impersonation, and no host role: it read its target from the path and checked neither
the actor nor whether one was supplied. It was a leftover of D-35's dual-transport
period, it had no caller, and **V5 has now deleted it** (D-50). So the sequence ran V5
before V3 — the `attach` gap is the harder of the two to exploit, not the easier, and
it is now the **only** remaining route to host-only actions without host authority.
V3 is what closes it.

## Backlog

### V1 — Host handover · `DONE`

**Goal:** the host hands the host role to another participant and stops being
host. It is a *move* of permissions, not a grant: exactly one host at a time, no
co-hosts, no residue. The new host can hand it on again, and so on indefinitely.

Fits the domain as it stands — `Room` already holds a single `host_id`, so the
handover is one assignment. Unlike the disconnect-driven auto-transfer (D-13) there
is **no** transient `host_id: null`, so the host UI does not flicker through an
unowned state.

**Decided — the outgoing host becomes a full participant, and votes.** Once they
hand over they are an ordinary participant in every respect, **including if they had
opted out of voting while host**. The opt-out was a facilitator privilege attached to
the role, not to the person; it does not follow them out of it.

This needs **no new code**, because both sides already key on *who is host right
now* rather than on a stored per-participant flag:

- Domain — `cast_vote`'s guard is `participant_id == self.host_id and not
  self.host_voting` (`models.py`). The instant `host_id` moves, the outgoing host no
  longer matches it and may vote.
- UI — the eligible-voter set is
  `participants.filter(p => host_voting || p.id !== host_id)` (`Room.tsx:93-96`), so
  they reappear in the deck and in the vote-progress denominator on the next
  snapshot.

The mirror case **is** the real work: **reset `host_voting` to `true` on handover**,
so the incoming host does not silently inherit an opt-out they never chose (which
would leave them with no deck and excluded from the denominator). There is a direct
precedent in the domain — `remove_participant` already does exactly this when a host
*leaves* and the role auto-transfers (`models.py:125-126`, D-13). A deliberate
handover matches that path. Both hosts end up voters; either can opt out afterwards.

Visible consequence, mid-round: the denominator grows as the outgoing host rejoins
the voter pool — a round at `5/6` becomes `5/7`. This does **not** block anything:
`reveal` is unconditional in the domain, with no all-voted gate (D-12), so the host
can still reveal a partial round and the stats cover the votes actually cast.

**Settled while building:**

- **Timing — legal at any point, including after reveal.** Confirmed, and it needed
  an argument rather than a shrug: `RoundRevealed` guards the *inputs* to
  `results()` (`revealed` and `votes`), and a handover writes neither, so a revealed
  round survives it byte for byte. Decisive point against locking it — a host who
  reveals and then needs to leave would have to `reset`, destroying the results the
  room is reading, in order to hand over. See D-45 and `RoundRevealed`'s docstring.
- **Feedback — snapshot-only.** No new frames, no toast, no live-region
  announcement. The D-36 broadcast already makes host controls appear for the new
  host and vanish for the old one, which is the feedback. S20 owns interaction
  polish and S22 owns the copy; building either here would fragment them.

**Surface:** a per-row action in the S23 participants roster (which was built as
the anchor for exactly this — its rows are inert text and the panel is
`role="group"` until real menuitems exist). Any new UI follows
[06-design-language.md](06-design-language.md) — monochrome, state by border and
content rather than color.

**Refs:** FR-20 (to write), FR-7, FR-14 · D-13, D-14 · roster anchor S23.

### V2 — Remove a participant · `DONE`

**Goal:** the host removes a participant from the room.

With no accounts, removal is **not a ban**: the removed person still has the room
code and can rejoin as a fresh participant (D-15). Scoped as "remove," and that is
**enough for v0.1** — a real ban needs per-room state that does not exist today, so
it stays out of scope in [02-current-scope.md](02-current-scope.md). Pinned by test
rather than left implicit, so a later reader finds a decision instead of a gap.

`remove_participant_by_host` guards (`_require_host`, self-target, membership) and
delegates to the same `remove_participant` primitive the disconnect path uses — the
same effect under different authority. That delegate's D-13 auto-transfer branch is
unreachable here, and provably: it fires only for the id the self-target guard
rejects. So a removal never moves the role and never empties the room, which is why
it needs no `empty_since` stamp and stays out of `store.leave`.

**Settled while building** — the four open questions, in order:

- **What the removed participant sees — a dedicated `removed` slug and its own
  terminal notice.** Silence would have worked in the narrow sense: their socket
  closes, the client waits a second, re-`attach`es, is refused, and lands on the
  rejoin prompt. But the honest reason would be overwritten by a misleading
  "Participant is not in this room" after a detour through "reconnecting", so a
  removal would read as a stale session. The slug is protocol, not copy — S22 still
  owns the wording, which lives server-side beside the slug it travels with. This
  made `removed` the **first mid-session error that is terminal**, a category the
  client's phase-based terminality could not express; see D-47.
- **Socket teardown — `apply_and_evict`, which *uses* the single-owner logic rather
  than dodging it.** It detaches the target's socket from the manager map itself, so
  the removed socket's own `finally` gets `False` from `unregister` and correctly
  skips a leave for someone already gone — no duplicate broadcast, nothing to
  suppress. The detach deliberately precedes the broadcast, so the removed client
  never receives a snapshot of a room it is not in.
- **Rejoining immediately — accepted, no cooldown.** Consistent with D-15 and with
  the code being a room's only barrier (D-29). The terminal notice means they are not
  *handed* a rejoin form, but the link still works.
- **Interaction with V1 — confirmed, and tested both ways.** The host cannot remove
  themselves (constraint 3); a host who wants out hands over first, then leaves. And
  authority follows the role: after a handover the new host can remove, including
  removing whoever used to be their host.

One question the item did not carry but had to answer: **it is not locked after
reveal**, though unlike a handover it genuinely rewrites a revealed round — dropping
the target's vote changes the average and consensus. That is the leave path's
documented, tested behavior reached by a deliberate trigger, and locking it would
force a `reset`, destroying the results the room is reading, as the price of removing
someone. See D-47 and `RoundRevealed`'s docstring.

**Surface:** a second per-row action in the S23 roster, beside V1's "Make host" and
with the same two-step confirm. The row became **two fixed button positions — Make
host, then Remove — and the confirm controls keep fixed sides: Cancel first, Confirm
second, whichever action is pending.** So a pending confirm hides both actions rather
than disabling one, and the accept/reject pair is always in the same place. Neither
button ever moves; the trade is that only the removal is a press-twice-in-place, and it
required real focus management to keep the handover completable from the keyboard —
see D-47, which records both. Monochrome per
[06-design-language.md](06-design-language.md) — a person-minus glyph rather than a
trash can, since removal deletes nothing.

**Refs:** FR-21, FR-5, FR-6, FR-17 · D-15, D-18, D-47 · roster anchor S23.

### V4 — Host-chosen card values · `DONE`

**Goal:** the host picks the room's card values when creating it. One optional
field under "Your name" takes them comma-separated — `1, 2, 4, 8, 12, 16` — and
left blank the room gets the Fibonacci deck it has always had. **Sequenced after
V2**; independent of V3, and of every carried-forward slice except the copy in S22.

This is the first departure from a deck that is a *global constant*, and that is
where the work is. Today `config.FIBONACCI_DECK` (`config.py:30`) is the source of
truth, `cast_vote` validates against it directly (`models.py:198`), and `VoteDeck`
renders from the client-side mirror in `lib/deck.ts` without consulting the room at
all (`VoteDeck.tsx:45`). The deck has to become room state and ride the snapshot.

**Decided up front** — settled before the item was written, not open questions:

- **Numbers only.** Every value must parse as a non-negative number; decimals are
  allowed, so `0, 0.5, 1, 2` is a legal deck. No `?`, no coffee card, no T-shirt
  sizes: D-8 ("cards are numbers") survives V4 intact and only D-7 ("Fibonacci
  only") gives way. T-shirt sizing and special cards stay out of scope.
- **Fixed at creation.** `Room.deck` is written once and never changes. That buys
  the whole slice out of the hard question — no cast vote can ever hold a card that
  has left the deck — and means no new host-only frame, no mid-round invalidation,
  nothing in the roster or host controls. A host who wants different values makes a
  new room.
- **One free-text field.** No preset picker, no live preview. An optional input
  under "Your name" in `CreateRoomForm`, blank-means-Fibonacci as its help text.
  S22 owns the final wording; follow [06-design-language.md](06-design-language.md)
  for the field itself.

**Validation** — proposed here, and the part most worth a second look before
building. **Built as proposed, every rule intact**, and it lives in
`backend/app/rooms/deck.py` rather than inline in `router.py`: same boundary (the
create request model calls it), but the rules are ~60 lines with their reasoning
and `router.py` is a routes file. A bad deck is a `422` on creation rather than a
room that is already broken:

- Split on commas, trim each segment, drop the empties — `1, 2, ,3` is a three-card
  deck and a trailing comma is not an error.
- Each value parses as a number, is non-negative, and stays legible on a card
  (proposed: below `1000`, at most 6 characters).
- Between **2 and 15** cards. One card is not a vote; the Fibonacci deck is 8, and
  the card row still has to read well in a 30-person room.
- **Duplicates rejected, not silently deduped** — `1, 1, 2` is a typo, not an
  intent. This is the debatable one: dedup is friendlier, rejection is honest.
- Each value **normalized to a canonical string** before storage — `1.0` → `1`,
  `01` → `1`, `.5` → `0.5`. Not cosmetic; see the consensus note below.
- Order **preserved as entered**, not sorted. The host's sequence is the deck's
  sequence, and a host who types `8, 5, 3` meant it.

**Bounds since revised.** The numbers above are what V4 proposed and shipped;
**D-49** later narrowed them to `1`–`999` per card and 2–12 cards, which also drops
the `0` from the default deck. The rules' *shape* is unchanged — this list still
describes the validator — but for the current figures read FR-22, not this item.

**Landmine — `results()` parses cards as `int`.** `models.py:342` does
`int(card)`, so the first reveal in a room whose deck contains `0.5` raises
`ValueError` — a 500, not a domain error, and only on reveal, so the room looks
fine right up until it doesn't. It has to become `float(card)`. Display needs
nothing: `Results.tsx:34` already formats with `toFixed(1)`. Consensus is the
mirror case and the reason normalization is load-bearing — it compares the card
*strings* (`len(set(self.votes.values())) == 1`), so an un-normalized deck holding
both `1` and `1.0` would let two voters who actually agree fail to read as
consensus.

**Shape of the work:**

- **Domain** — `Room` gains `deck: tuple[str, ...]`, defaulting to
  `config.FIBONACCI_DECK` so every existing construction site and test keeps
  working; `store.create()` accepts it and threads it through; `cast_vote`
  validates against `self.deck`. `InvalidCard` keeps its meaning but its docstring
  and message should stop saying "the Fibonacci deck" (`errors.py:24`).
- **Read side** — `RoomView` carries `deck`, which is the whole distribution
  story: it reaches every client in every snapshot (D-36), so a reconnecting
  participant gets it for free and `session.ts` has nothing new to persist.
- **Frontend** — `types.ts` gains the field, `VoteDeck` renders the snapshot's deck
  instead of importing the constant, and `lib/deck.ts` demotes from *mirror of the
  only deck* to *mirror of the default*. Its comment that drift between the two
  arrays is the only route to `invalid_card` stops being true and needs rewriting —
  though note `invalid_card` stays unreachable from the UI regardless: the deck is
  immutable and arrives in the snapshot, so a client can only click cards the room
  actually holds. It remains the guard against hand-crafted frames.
- **Tests** — `VoteDeck.test.tsx`, `Room.test.tsx`, and `Results.test.tsx` all
  hardcode the eight Fibonacci values and will need the deck supplied rather than
  imported. New coverage: a validation table at the boundary, `cast_vote` against a
  custom deck (accept + reject), a revealed round with decimal cards to pin the
  `float` fix, and an e2e that creates a room with `1, 2, 4, 8, 12, 16`, votes, and
  reveals.

**Settled while building** — the questions the item did not carry:

- **Blank is not the only way to mean blank.** `parse_deck` drops empty segments,
  so `,,,` and `   ` reduce to no cards at all. That is the *default*, not a "2 to
  15 cards" rejection: the field is optional, and a host who typed only separators
  named no values. Rejecting it would be technically defensible and useless.
- **The bounds are checked against the normalized form, not the input.** `1_0` is
  two characters over the wire and one card (`10`) on a card face, and the face is
  what "at most 6 characters" is about. This also makes `float`'s permissiveness
  harmless rather than a hole — `1e2` is accepted and stored as `100`.
- **`nan` and `inf` needed naming.** Both parse as floats, and `nan` fails every
  comparison, so without an explicit finiteness check it would have fallen through
  the range guards and been reported as "negative", which it is not.
- **The client does not pre-validate — only the server does.** `CreateRoomForm`
  sends the raw string and renders the `422` inline. A mirror of these rules on
  that side could only drift from the one that decides, and unlike the topic and
  name bounds (`lib/limits.ts`), most of them are not expressible as an input
  attribute anyway. The `maxLength` on the field is the single exception: it mirrors
  `MAX_DECK_INPUT_LENGTH`, which is a length and nothing more.
- **A leaked pydantic prefix became user-visible copy, and was fixed here.**
  Every custom-validator message reaches the client as `"Value error, <message>"`.
  That was latent while a `422` meant a name the UI had already blocked; a mistyped
  deck is an ordinary outcome, so `api.ts` now strips the prefix. An implementation
  detail escaping into the UI is a defect, not a wording choice — so it belongs
  here rather than in S22, which still owns the field's label and help text.

**Docs moved with it — all done:** FR-9 now states numbers-only with Fibonacci as
the *default*; **FR-22** states the host's creation-time choice, under a new
`### Room configuration` heading; **D-48** records the decision, partly supersedes
D-7, and leaves D-8 explicitly standing (both entries carry a forward note, so a
reader who lands on D-7 first is not misled). 02-current-scope's `Deck` row is
rewritten, a `Card values` row joins it, and the *Planned* section is now empty.
04-glossary's **Deck** entry is no longer MVP-tense.

**Refs:** FR-22, FR-9, FR-16 · D-7, D-8, D-16, D-48 · `deck.py` (new),
`config.py`, `models.py` (`Room.deck`, `cast_vote`, `results`), `views.py`,
`VoteDeck.tsx`, `CreateRoomForm.tsx`, `lib/deck.ts`.

### V5 — Retire the unused HTTP routes · `DONE`

**Goal:** delete the S3/S4 HTTP round routes and the T1 `/ws` echo. This is D-35
being *executed*, not revised: the dual transport was time-boxed from the day it
was chosen — kept so the domain stayed `curl`-testable while the socket was
unproven, "dropped once the frontend is live." The frontend has been live since
S7, so the period is spent. NFR-1 already describes the end state ("real-time
state is delivered over WebSocket; room creation may use HTTP"), so **no new FR** —
this brings the code into line with a requirement it already has.

**Sequenced before V3**, and that is the one substantive change to the plan.
`DELETE /{code}/participants/{participant_id}` (`router.py:222`) takes its target
from the *path*, applies **no host check and no actor check at all**, and calls
`store.leave` directly. Every participant id ships in every snapshot
(`views.py:82`), so anyone holding the room code can eject any participant, host
included, over plain `curl` with no socket — and `allow_origins=["*"]` with
`allow_methods=["*"]` (`main.py:122-127`) lets a web page preflight it too. V2 built
`_require_host` plus a self-target guard for exactly this operation over the socket;
the HTTP door beside it has none. That is strictly worse than the `attach` gap V3
exists to close, so closing it first is the cheaper half of the same problem — and
V3 then shrinks to `attach` plus one string in `session.ts`.

**Nothing in the app calls any of them.** `lib/api.ts` makes exactly two HTTP
requests — `POST /rooms` and `POST /rooms/{code}/participants` — which stay (D-5,
D-38). `e2e/tests/capacity.spec.ts:14-31` uses those same two to fill a room and is
unaffected. Verified by search, not by assumption.

**Routes to delete:** `PUT /{code}/item`, `PUT /{code}/vote`,
`PUT /{code}/host-voting`, `POST /{code}/reveal`, `POST /{code}/reset`,
`DELETE /{code}/participants/{participant_id}` (`router.py:176-234`), and the
placeholder echo socket (`main.py:139-151`).

**Related code that goes with them** — the part most easily left behind:

- **Request models** `SetItemRequest`, `CastVoteRequest`, `HostVotingRequest`,
  `HostActionRequest` (`router.py:79-118`). Each exists only for a route above.
- **`_require_room`** (`router.py:134`) becomes dead. Create goes through
  `store.create` and join raises its own 404 from `store.join`, so all six
  remaining callers leave with the routes.
- **The `apply_and_broadcast` import** in `router.py:19`, but *not* the helper —
  `ws.py:282` still uses it. `broadcast_room_state` stays too; join calls it
  (`router.py:172`).
- **`messages.py:140`** explains `SetItemFrame`'s length bound as mirroring "the
  HTTP `SetItemRequest`… (D-36 parity)". That reference dangles once the model is
  gone; the bound stops being parity and becomes simply the boundary's rule.
- **`_ROOM_ERROR_STATUS`** (`main.py:95-108`). After this, `RoomFull` is the only
  entry reachable over HTTP — `UnknownParticipant`, `HostNotVoting`,
  `RoundRevealed`, `InvalidCard`, and `NotHost` join `CannotTargetSelf` in being
  mapped but unreachable. **Broaden that comment rather than prune the table**: it
  already argues for keeping a complete statement so a future route cannot fall
  through to a 500, and that argument now covers almost every row. The handler
  itself stays.
- **Docstrings that describe the dual transport as current:** `router.py:1-11`,
  `main.py:3-7`.

**Tests** — 39 of 279 backend tests touch these routes, and the coverage is almost
entirely duplicated at domain level, which is what makes this cheap:

- **Delete outright — 32 tests.** `test_voting_api.py` (13), `test_reveal_api.py`
  (11), `test_lifecycle_api.py` (8). Each has a domain counterpart that is strictly
  richer: `test_voting_domain.py` (22), `test_reveal_domain.py` (24),
  `test_lifecycle_domain.py` (18). The residue is **HTTP status-code mapping**,
  which only matters for routes that still exist — create/join keep theirs in

- **Mechanism swap, assertion survives — 3 tests.** `test_rooms_api.py:113` (V4's

essentially unmoved. The `/ws` echo had no tests at all. Frontend (188) and e2e

**Settled while building** — the two places the plan above needed amending:

- **One of the four D-36 parity tests was kept, in reduced form, rather than
  deleted.** The plan was right that HTTP↔WS convergence stops being falsifiable with
  one transport, but `test_http_presence_reflects_to_socket` was doing a second job:
  the surviving HTTP *join* still broadcasts to sockets already in the room, and it is
  the only non-socket mutation left that reaches connected clients. Nothing else
  covers it — the existing join fan-out test sends a WS `join` frame, not an HTTP POST
  — so deleting all four as written would have dropped the last test of `join_room`'s
  `broadcast_room_state`. It survives as `test_http_join_reflects_to_socket` with the
  removal half cut and the reason recorded in its docstring.
- **A fourth dangling rationale, not on the list above: `ws.py`'s
  `suppress(UnknownParticipant)`.** Its comment cited "an HTTP DELETE for the same
  pid" as the case it absorbs, and that route is now gone. Checking whether the branch
  is still reachable at all: it is not, and provably — a host removal detaches the
  socket before the domain leave, so `unregister` returns `False` and the suppress is
  never reached, and a swept room fails the `room is not None` guard above it. Kept
  anyway, with the comment rewritten to say so, because it sits in a `finally` on the
  disconnect path: if some future caller removes a participant without detaching, the
  cost of having pruned it is an exception that denies every *other* client in the room
  their leave broadcast. Same judgement as `_ROOM_ERROR_STATUS`, for the same reason.

**Decision entry written — D-50** records the retirement, what became of the D-36
parity tests (including the kept one), and the unauthenticated-`DELETE` finding as the
reason it was sequenced ahead of V3. D-35 is *fulfilled*, not superseded — it
anticipated its own end, so it gained a forward note rather than a correction, and
D-36 gained one noting its convergence claim is no longer testable.
