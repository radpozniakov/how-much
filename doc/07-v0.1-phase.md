## Goal

Give the host real control over the room — hand the role to someone else, remove
a participant, choose the room's card values — cut the retyping a returning user
does, and close out the deployment, polish, accessibility, and copy work still
outstanding. The target is a v0.1 you can hand to a team and deploy.

## Contract status

This phase adds functional behavior, so [01-requirements.md](01-requirements.md)
and [02-current-scope.md](02-current-scope.md) move with it rather than being
frozen. All contract additions are written: **FR-19** (self-rename, backfilled
for D-42), **FR-20** (handover, D-45), **FR-21** (removal, D-47), **FR-22** plus

V7 adds no contract: it is presentation only.

## Standing design constraints

Carried from the S23 security review. V1/V2 honored them; any new frame must too:

1. **Authorize in the domain**, via `_require_host`, exactly like
   `set_item`/`reveal`/`reset`. The frontend's `isHost` is a rendering affordance,
   never the boundary.
2. **Frames carry a target id and no actor id.** The actor is the socket's
   handshake identity — so a client cannot attribute an action to someone else
   within its own socket.
3. **Validate the target** in the domain: it must be a current member, and the
   host cannot target themselves.
4. **Log actor / target / room / outcome** for actions that remove people or move
   authority, so a session is explicable after the fact.

## Known limitation — `attach` impersonation

Accepted, not fixed. `attach` authenticates on `participant_id` alone (membership
only) and `room_view` broadcasts every participant id plus `host_id`, so any
member can open a second socket as another participant — the host included — and
drive host-only actions. V1 and V2 raised the stakes: a displaced host has no
route back while the impostor stays connected, and a removed participant is out
until re-invited (blunted by removal not being a ban, D-15, and by every removal
being logged, constraint 4). Since V5 deleted the unauthenticated HTTP routes
(D-50), this is the **only** remaining route to host-only actions without host
authority — confirmed by a working proof-of-concept during V5's review. The fix
is **V3**.

Every attacker here is already an invited teammate: the unguessable code is a
room's only barrier (D-29) and the tool is no-auth throughout (D-9).
**Decided (D-51):** the tool will be deployed as an internal team tool, so V3 is
**nice-to-have, not a blocker** on v0.1. Revisit if the tool ever goes somewhere
less trusted than a team room.

## Backlog

### V1 — Host handover · `DONE`

The host hands the role to another participant — a *move*, not a grant: exactly
one host at any moment, the outgoing host becomes an ordinary voter, the incoming
host gets `host_voting` reset so they never inherit an opt-out. Legal at any
point in a round, including after reveal. Surfaced as a per-row roster action
with an inline two-step confirm. Rationale and consequences: **D-45**; the
panel's ARIA shape: **D-46**.
**Refs:** FR-20, FR-7, FR-14 · D-13, D-45, D-46.

### V2 — Remove a participant · `DONE`

The host removes another participant: the leave path under host authority, so
the target's vote goes with them and their connection ends with a terminal
`removed` notice. Not a ban — they can rejoin at once with the code they hold.
Second per-row roster action, same two-step confirm on fixed button positions.
Rationale, socket-teardown ordering, and the confirm-row trade-offs: **D-47**.
**Refs:** FR-21, FR-5, FR-17 · D-15, D-18, D-47.

### V3 — Per-participant session token · `TODO` · nice-to-have, not a blocker (D-51)

Close the `attach` gap above — since V5 it is the entire authorization
perimeter, and this is the last route to host-only actions without host
authority. Shape, per the S23 review: `Participant` gains a `token`
(`secrets.token_urlsafe()`); create/join return it to that caller only;
`room_view` never carries it; `attach` requires it and compares with
`hmac.compare_digest`, keeping the failure response identical to the unknown-id
case so it is not a membership oracle. Client-side, `session.ts` already
persists `{code, participantId}` and stores one more string. Not user-visible,
so the no-account stance of D-9 is untouched.
**Refs:** D-9, D-29, D-38, D-39, D-50.

### V4 — Host-chosen card values · `DONE`

The host may name the room's card values when creating it, in one optional
comma-separated field; left blank, the room gets the Fibonacci default. The deck
became room state riding the snapshot, validated only at the create boundary,
and fixed for the room's life. Bounds were tightened after shipping — `1`–`999`,
2–12 cards, the default lost its `0` (D-49); for current figures read FR-22.
Rules and rationale: **D-48**, **D-49**.
**Refs:** FR-22, FR-9, FR-16 · D-7, D-8, D-48, D-49.

### V5 — Retire the unused HTTP routes · `DONE`

Deleted the S3/S4 HTTP round routes, the unauthenticated participant `DELETE`,
and the T1 `/ws` echo — D-35 *executed*, and no new FR since NFR-1 already
described the end state. Sequenced ahead of V3 because the `DELETE` route was
exploitable with a `curl` one-liner, and review showed the five round routes
were forgeable too (identity from the request body). Backend 279 → 246 tests;
frontend and e2e untouched. Findings, test fallout, and the mutation-testing
lesson: **D-50**.
**Refs:** NFR-1, NFR-6 · D-5, D-35, D-36, D-50.

### V6 — Recalled name and card values · `DONE`

The browser offers back what the user last submitted: their display name wherever
a name is asked for (create, join, the rejoin prompt) and their card values on the
create form. A per-device `localStorage` record in a new `lib/recall.ts`,
deliberately separate from the per-tab `sessionStorage` identity of D-39 — merging
them would make every new tab re-attach as the same participant. Written on
successful submission only, including a rename (FR-19); read once at mount via a
`useState` lazy initializer, after which a recalled value is ordinary input. Also
in this slice, and coupled to it: the card-values field takes the Fibonacci default
as its **placeholder**, which shows precisely when no deck is recalled. Rules, the
rejected alternatives, and the two questions building it settled — the patched
write and where a rename's write lives: **D-52**.
Frontend 188 → 213 tests, e2e 44 → 52; backend untouched. Two of the new tests are
guards rather than feature tests: two tabs of one context must share recall and
*not* identity, which no existing e2e spec covered because every other one is a
single tab per context; and a rename committed after the socket drops must remember
nothing, which is the bug review caught in the first attempt.
**Refs:** FR-23, FR-19, FR-22, FR-9 · D-9, D-39, D-52. Frontend-only — no
protocol, domain, or backend change.

### V7 — Visual refinements · `DONE`

Four corrections to shipped surfaces, batched because each is small and all of
them are `main.scss` plus the odd bit of markup. No new behavior, no contract
change; doc/06 governs, and the monochrome rule (grey is not colour) is not
relaxed by any of them. Three of the four shipped differently from the plan after
the panel was reviewed in the browser — the items below are what shipped, and
**D-53** carries every divergence and why.

1. **The idle roster actions lost their chrome; hover still inverts.** Make host
   and Remove are borderless with a transparent background and an `--ink` glyph.
   The planned `--wash-hover` fill did **not** ship; hover stays the solid-ink
   inversion these buttons always had, and the token is unused again (D-53,
   doc/06). **Cancel and Confirm are unchanged:**
   an armed row still reads as bordered Confirm against
   borderless Cancel, so the emphasis difference that tells a host which press
   counts survives intact. This narrowed the panel-scoped override rather than
   deleting it — it exists because the header's `--surface` hover fill is
   invisible against the panel's own `--surface` background. Every state now
   hovers identically, so the inversion lives once on the shared rule. The
   consequence to hold onto is that arming a row changes a button's border as
   well as its glyph — a bigger visual jump than before, and the thing to look at
   first.
2. **Only the host's row keeps a separator, and only when there is someone to
   separate from.** The `& + &` hairline between rows is gone; the host — always
   sorted to the top — gets a single rule under their row, with `--space-2` above
   and below it. Alone in the room the host's row drops both the rule and its
   padding, since a line under the only row is a line under the whole list. The
   panel is host-only, so that row is also the "me" row. `hostId` can be `''`
   during the transient unowned window, in which case no row is the host's and
   the list renders with no separator at all.
3. **The name keeps its badge; whatever ends the row goes right.** The row was
   `justify-content: space-between`, so with a short name the badges drifted to
   the middle. Now the name and the badge qualifying it sit together on the left,
   and the row's trailing element — the last badge, or the two action buttons —
   is pushed to the right edge, so both land in the same column. The name's
   ellipsis (`min-width: 0`) and the two fixed action slots are undisturbed.
   Row `gap` came down to `--space-2`; the rule that tightens the button pair
   subtracts that same token and has to keep tracking it.
4. **The two terminal room views got the landing treatment.** "Room {code}" for
   both the host-removed notice and the swept-room message carries the
   `landing__title` style and the message the `landing__description` style. The
   third clause — matching "Back to start" to HostControls' "Reveal cards"
   (`.host-reveal__btn`) — was **already true and needed no code**: that class
   carries no declarations, so both buttons have always been the global `button`
   rule (D-53). Two things the treatment did change beyond the plan: the `.card`
   wrapper is gone from both views — the room is over, so there is no surface left
   to sit on, just the title, what happened, and the way out — and the button,
   which sat flush against the message, has `--space-4` above it. Both views are in
   `pages/Room.tsx` and stay structurally identical on purpose. **Does not** close
   S21's finding that neither view takes focus when it replaces the room — that
   stays S21's.

**Refs:** FR-20, FR-21 · D-40, D-45, D-46, D-47, D-53 · doc/06. Independent of V6
and of everything below. The stage's "Set a topic…" placeholder keeps
`--ink-muted` — lightening it was considered and **dropped**, not deferred.

## Out of scope (this phase)

Unchanged from [02-current-scope.md](02-current-scope.md) apart from the features
above: no accounts or authentication, no persistence or history, no
backlog/ticket management or integrations, no distribution charts, no timers, no
i18n, no mobile-native. Banning a removed participant is explicitly **not** in
V2. Spectators as a distinct role remain out.

V4 retires "no multiple or custom decks" only as far as its own scope goes. Still
out: **T-shirt sizing and special cards** (`?`, coffee) — decks are numbers-only —
along with **named or saved decks**, **more than one deck per room**, and
**changing the deck after creation**.
